# Architecture

Core has no package references or dependencies on Avalonia, SDL, or Windows MIDI Services. It
contains normalized input/MIDI contracts, scale and configuration models, held-note state, mapping,
safe output coordination, octave modifiers, discrete stick gestures, and versioned JSON profile models.
Continuous expression is generated by Core's `ExpressionEngine`; filesystem persistence belongs to App services.

Chord mode stays in Core. `ChordResolver` builds root-position triads from a seven-note harmony
collection or a selected explicit shape; `NoteSpelling` handles letter/accidental naming without
platform dependencies. One held `NoteRecord` represents a physical gesture with one or three
voices. Snapshots flatten held voices for observation while last-active group records retain the
complete chord. The existing channel/pitch ownership ledger coalesces shared voices; expression
selects each chord tone and resolves shared pressure by the latest group selection. Start changes
the immutable chord configuration on its press edge; profile capture includes that current mode.

## Thread ownership

```text
Process main thread: SDL initialization and bounded event pump
  → SDL-specific control normalization
  → GamepadInputEvent (readonly value type, monotonic timestamp)
  → Core MidiInstrument → MappingEngine → MidiEvent
  → IMidiOutput.TrySend (bounded nonblocking submission)
  → Windows backend queue → dedicated MTA thread → Windows MIDI Services

Separate Avalonia STA thread:
  → 30 Hz input/musical/activity snapshots
  → ViewModels → controller drawing and note monitor
  → 10 Hz MIDI status/topology revision observation

User controller selection → queued command → SDL owner thread
User output selection → async Core transition → MIDI owner thread
Settings draft → validated immutable configuration → Core configuration transition
```

SDL native handles belong exclusively to the process main thread. Avalonia runs separately to
honor SDL's main-thread pump requirement while keeping UI work outside note generation/delivery.
Another platform can supply another host and implement the same input/output contracts.

`MidiInstrument` uses a short lock to serialize engine processing, configuration changes, cleanup,
and snapshot capture. It performs no native or file I/O while holding that lock. `InstrumentSession`
subscribes input directly to Core and records generated value events in an eight-entry ring with
its own short lock. Musical state is captured before acquiring the ring lock to avoid inverse lock
ordering. Presentation formatting/collection changes happen after those locks are released.

The engine remains independent of scheduling and single-owner. `WindowsMidiOutput` owns a bounded
4096-entry FIFO; live sends use `TryAdd` with no queue-capacity wait. Control requests may await
queue space off the input/UI thread. MIDI API activation, discovery, native sends, connection cleanup,
and session lifetime belong to one dedicated MTA thread. Queue overflow disables output and initiates
cleanup instead of discarding a release and continuing. Native callbacks publish fault/topology flags;
they do not invoke UI or musical logic directly. Endpoint enumeration is event-driven, with Added,
Removed, Updated, and EnumerationCompleted notifications. UI polling reads cheap snapshots/revisions.

SDL waits at most 4 ms and drains bounded event batches so cancellation/selection cannot be starved.
Each selected-device loop iteration emits a normalized Tick directly to the musical engine. This
settles smoothing and sends the latest rate-limited value even if physical input stops arriving.
Ticks bypass the observation buffer and do not count as physical input changes.
Analog values and button edges are normalized and identical values suppressed. Device-list allocation
occurs on topology changes; observation snapshots allocate independently. Live event values/ring/queue
entries are structs. No high-frequency input/MIDI path performs file I/O or UI work.

## Musical state

Immutable configuration is separate from runtime state. `MappingEngine` consumes abstract physical
controls and supports scale-degree/fixed-note actions. Every press records exact channel, MIDI pitch,
velocity, note group, sequence, and physical control. Releases use this record, never current settings.
Shared channel/pitch identities are coalesced until the last physical owner releases. Changing
root/scale/octave/mapping/channel affects future presses only. State tracks held physical controls,
exact notes, last triggered global/group notes, and latest active D-pad/face notes with fallback.

Milestone 4 adds configurable momentary octave/semitone sources and `DiscreteStickLatch` hysteresis.
Default left-stick Up/Down applies +1/-1 octave until neutral; Left/Right changes the persistent
octave by -1/+1 once per excursion;
held LB/RB applies -1/+1 semitone.
Both offsets resolve only at Note On and never retune held records. Persistent
octave offset is separate from immutable configuration and survives lifecycle cleanup; temporary
modifiers, held records, selections, and latches clear. One stick action fires per excursion until
both axes enter neutral. Optional last-note sharp/flat actions release and retrigger the globally selected held note on its
original channel/velocity, then updates that physical control's ledger and group history. Shared
pitches still use ownership coalescing. Released selections update history without generating sound.
Resolution applies transposition before MIDI bounds checking; no unintended pitch clamping occurs.

The scale catalog contains 13 immutable presets; custom interval definitions use the same resolver.
Degree mapping wraps across the selected scale's length, including pentatonic/blues/chromatic scales.
Melodic Minor uses its ascending intervals in both playing directions.

## Configuration editing

The Settings window uses separate draft ViewModels for scale, button assignments, discrete stick
actions, and expression responses. Apply builds and validates a complete immutable candidate before
calling `InstrumentSession.UpdateConfiguration` and Core's coordinated transition. Invalid drafts
never alter the running engine. Reset loads defaults into the draft; Close discards unapplied edits.
The main view observes applied configuration, including channel changes, without submitting edits.

Editor ViewModels translate presentation fields into configuration models; note resolution, held-note
ownership, modifiers, expression generation, and cleanup remain in Core. Settings can be open while
input continues directly through the existing SDL/Core/MIDI path. Panic is available in the dialog.
Applied settings persist when the user saves a profile. Profile loading resets the persistent octave
offset explicitly, even when the saved configured octave matches the previous configuration.
Existing held records and physical edge state remain valid through this transition.

## Profiles and storage

`InstrumentProfile` stores a schema version, GUID, name, immutable configuration, and optional device
preferences. `ProfileJson` uses System.Text.Json with named enums and explicit note-action discriminators.
Validation rejects unsupported versions, unknown/duplicate properties, malformed configuration, and
oversized JSON before applying anything. Known scale definitions canonicalize to Core presets;
custom interval definitions remain supported. Runtime note/filter/controller state is never serialized.

`IProfileStore` separates the storage contract from platform-independent models. App's `FileProfileStore`
uses GUID file names under LocalApplicationData, serialized writes, flushed temporary files, and
same-directory replacement. A failed replacement leaves the prior file intact. Library enumeration
and writes run on background tasks; no file I/O occurs in the input/MIDI path. Bad library files are
reported individually and left intact. A built-in read-only default remains available.

The Profiles ViewModel orchestrates user requests through the store and supplied composition callbacks.
Apply remains in Core. Saving captures the current persistent base octave without temporary modifiers.
Import allocates a fresh ID; export cannot overwrite the library through its file-picker path. Native
Avalonia pickers are isolated behind `IProfileFileDialogs`, allowing actual button-command tests with
test paths. The last loaded/saved ID restores on startup; unsaved settings are not auto-saved.

Preferences select a uniquely named available controller and a saved MIDI endpoint. Missing/ambiguous
controllers are deselected; unavailable endpoints remain unconnected with a visible message. Changing
an existing output uses Core's safe disconnect transition. Loading a profile never auto-connects MIDI.
Device name matching is a documented fallback until the input backend exposes durable hardware identity.
Panic remains available independently of storage operations/errors.

## Continuous expression and output coordination

Milestone 5's `ExpressionEngine` owns four time-based smoothers and fixed-size MIDI value ledgers.
`TimeProvider` supplies monotonic time and deterministic tests. Trigger pressure follows the latest
active physical record per group, including its original pitch/channel. Selection changes clear
previous pressure and immediately apply the current trigger to the new/fallback target; the latest
physical owner wins when both groups share one MIDI 1 pitch. Release clears pressure before Note Off.
Pitch bend and timbre use the configured channel; center snaps to 8192/64 independently of smoothing
or rate limiting. Configuration/channel changes restore old destinations before applying new settings.
Cleanup cancels filters and deferred values, clears pressure, centers bend, and restores CC neutral.
Normalized CC messages carry optional reset metadata so the backend's sent-message ledger can also
reset a custom timbre CC on queue/send failures. Metadata does not alter UMP encoding.

`MidiInstrument` is the hardware-independent coordinator around that engine and `IMidiOutput`.
Output switching suspends input, releases notes/resets controllers, flushes accepted messages to the
old destination, disconnects it, and then connects the new one. New input during switching is not
replayed. Selected controller identity is retained separately so a fresh press works after cleanup.
Channel changes retain the old channel in held records. Panic stops tracked notes and resets used
channels while leaving the instrument ready for a fresh press. Backend failures clear state on the
next input/snapshot and require explicit output reconnect; there is no automatic note replay.

## Windows output

The Windows project pins the official preview `Windows.Devices.Midi2` SDK. C#/WinRT generates its
projection; conversion from Core messages to MIDI 1 channel voice UMP occurs only in that project.
The native API DLL/PRI deploy app-locally. The backend owns one `MidiSession` and one active
`MidiEndpointConnection`. Its ledger tracks successfully sent pitches and provides independent
cleanup on disconnect/failure/shutdown. Cleanup sends held Note Offs, CC123, channel pressure zero,
and pitch center 8192. Unreachable hardware receives best-effort cleanup only.

An output identifier comprises the native endpoint device ID plus its group index. Device function
blocks take precedence over group terminal blocks; active receiving/bidirectional groups are offered.
Groups and channels are zero-based internally, one-based in presentation. Diagnostic/unknown-output
endpoints are excluded. Hotplug notifications update selection choices without blocking input.
Endpoint removal is checked by the watcher as well as the preview connection callback.

Opening an output does not create a DAW input. A loopback pair or a synth/device endpoint must
already exist. The optional MIDI probe can create a temporary service route to a test-only receiver
that forwards into Windows' built-in software synth. This older synth API is confined to the probe;
the application backend always sends through Windows MIDI Services.

## Native input resources

Only the selected gamepad is opened. Discovery arrays are freed in `finally`; handles close on
switch/disconnect/shutdown. The gamepad subsystem is reference-counted and released after pumping
stops. Unsafe code is confined to SDL pointer interop and generated C#/WinRT code.

`Disconnected` precedes selecting another controller. `Selected` resets observation, then samples
physical values. Remapping resets/resamples the active controller. `Stopped` and `Faulted` clear
observed state and stop notes. SDL initialization failures leave the UI usable to read the error;
fatal input failures require restarting the app. Device open failures allow selecting another device.
SDL connection IDs distinguish identical devices but are ephemeral; durable profile identity remains
a later design using serial/vendor/product identity with a documented fallback.

## Remaining validation

Milestone 8 adds host-only OS checks, a named single-instance mutex, startup diagnostics,
Help and focus-scoped keyboard shortcuts. Panic commands call `InstrumentSession`; UI code
still does not generate MIDI. Release scripts publish self-contained x64 payloads with separate
RID lockfiles, native libraries, dependency notices, integrity manifests, ZIP and NSIS installer.
The per-user installer blocks changes while the named instance exists and explicitly removes
only packaged files on uninstall; saved profiles remain outside the install directory.

- Physical gamepads over USB/Bluetooth, optional controls, and simultaneous D-pad behavior.
- DAW-specific loopback/legacy-port visibility and measured hardware input-to-sound latency.
- Production preview API redistribution/update conditions and future in-box migration.
- Stable SDL native packaging: the pinned binding bundles SDL 3.5.0 development binaries.
  Startup and virtual-controller checks passed with this exact pair; review it before release.
